# ExeViewer 产品设计

## 定位与目标用户

面向 Linux 程序开发人员的 ELF 跨环境兼容性诊断工具。

核心问题：为什么在 A 平台使用 X 工具链构建的 exe/so，无法在 B 平台的 Y 运行环境下工作？哪里不兼容、证据是什么、应该修改构建产物还是运行环境，以及怎样验证修复？

加载过程、依赖图和反汇编是诊断依据。产品最终交付是可追溯的故障说明与修复建议。递归依赖树和搜索路径本身已有 libtree、rldd 等工具覆盖；差异化方向是将运行需求、目标环境、实际观测和环境对比连接成可验证的诊断流程。

## 典型使用场景

- 本地构建可运行，部署到旧发行版时报 GLIBC/GLIBCXX/CXXABI 版本缺失。
- 文件存在，但执行时报告找不到文件：检查 PT_INTERP 指向的动态链接器。
- 主程序的库存在，某个间接依赖缺失，或 RUNPATH 没有按预期作用于间接依赖。
- 同名 so 在不同环境中解析到不同路径，导致符号缺失或错误绑定。
- exe 启动成功，使用插件或特定功能时才在 dlopen/延迟绑定阶段失败。
- 构建环境引入目标 CPU 不支持的指令，或者依赖目标内核不支持的能力。

## 输入与证据边界

最终产物和目标运行环境是主要证据；工具链版本、编译参数、构建日志、sysroot 信息作为可选辅助输入。不能从 ELF 的编译器注释推断完整构建过程。

目标环境支持三个阶段性的入口：

1. 在目标机器直接检查产物与当前环境。
2. 离线检查目标 rootfs/sysroot，并显式提供 CPU、内核、工作目录、环境变量及启动方式。缺失的信息必须标为未知；不得悄悄用宿主机文件填充目标环境。
3. 保存 A/B 环境快照，对比库选择、版本提供情况、加载规则及实际运行结果。

分析 so 时应允许提供宿主 exe 和加载方式；独立检查 so 无法确定进程的完整符号作用域、预加载对象和命名空间。

## 诊断模型

| 层次 | 检查内容 | 主要证据 |
| --- | --- | --- |
| ELF 与架构 | 格式、位宽、机器架构、解释器 | ELF 头、程序头、目标环境 |
| 库解析 | NEEDED、RPATH/RUNPATH、预加载、缓存、默认目录、间接依赖、对象复用 | 动态表、环境、加载器规则、候选路径 |
| 符号与版本 | 所需符号、提供符号、版本定义与需求、弱符号和解析作用域 | dynsym、版本表、重定位和实际绑定记录 |
| ABI | 可证明的 ABI 不匹配，以及需要进一步验证的疑点 | 符号、调试信息、构建信息、运行观测 |
| 执行条件 | CPU 指令、内核能力、运行时加载 | CPU/内核快照、反汇编、执行证据 |

依赖关系、搜索尝试、映射顺序、初始化顺序分别建模。搜索规则需要保留请求方上下文，不能用一个全局路径列表替代。首期限定 Linux x86-64 + glibc，其他加载器明确报告范围限制。

每条诊断包含：稳定规则 ID、严重程度、确定性、受影响对象、引入链、需求和目标提供值、证据引用、影响阶段、修复方向及复验方式。

结论区分“发现阻断问题”“本次检查未发现问题”“证据不足”“不支持”。静态检查通过不能表述为程序必定可运行；符号版本满足也不能证明所有 ABI 和程序语义兼容。不得仅按版本字符串大小推断兼容性，应核对实际需求与定义。

## 两种证据获取方式

### 静态分析

只读取 ELF 与目标环境文件，不执行目标或其声明的解释器。构建递归依赖图，记录搜索规则来源、候选位置、命中结果与未解析项。保留限制，例如依赖 section metadata 时遇到无节区 ELF 应输出未知。

### 实际观测

由用户明确选择运行目标并提供参数。收集加载器诊断、必要的系统调用/审计事件，覆盖实际执行路径中的 dlopen、延迟绑定和初始化。标记观测手段、运行条件及其可能影响，并与静态推演逐项对照。没有观测到的路径不能判为不存在。

## 命令行是一等入口

诊断引擎产生结构化结果，CLI 和 TUI 复用同一个结果模型。CLI 无需键盘交互，可用于 SSH、脚本、日志和 CI；TUI 用于展开证据及探索关系。

### 当前已实现的入口

```sh
# 无交互，输出静态信息（文件路径或 PATH 中的 ELF 命令名）
ExeViewer --report ./app
ExeViewer --report /path/to/libfoo.so

# stdout 被重定向时自动采用报告模式
ExeViewer ./app > report.txt
ExeViewer --report ./app | head

# 显式进入已有交互界面，需要终端
ExeViewer --interactive ./app
```

报告包含文件路径、大小、SHA-256、ELF 类别、机器架构编号、类型编号、入口、解释器和直接声明的 NEEDED/RPATH/RUNPATH/SONAME。当前报告只做静态清单，不解析目标库、不执行目标、不调用加载器，不代表兼容性诊断已完成。无 .dynstr 节区元数据时明确输出依赖未知。报告模式对脚本返回非 ELF 错误，不自动改为分析脚本解释器。

当前契约：报告写 stdout，错误写 stderr；成功生成清单返回 0，读取/解析/执行模式错误返回非零。报告模式允许提前关闭的管道正常结束；输出没有 ANSI 控制序列。--report 与 --interactive 互斥。文本格式面向人阅读，尚不承诺机器解析稳定性。

### 诊断命令（已实现基础工作流）

```sh
ExeViewer diagnose ./app --rootfs ./target-root --target-path /opt/app --format text
ExeViewer diagnose ./app --rootfs ./target-root --target-path /opt/app --format json
ExeViewer compare --env-a a.json --env-b b.json --format json
ExeViewer trace --execute ./app --output-dir ./capture-001 -- --application-argument
```

诊断 JSON 已实现 `schema_version: 1`，包含产物哈希、环境来源、检查范围、依赖图、搜索证据、诊断和未完成检查。支持文本与 JSON、无 TTY、无 ANSI 控制序列。`compare` 对比两份诊断报告，`trace` 可导入日志或显式运行并采集 glibc 证据。

退出码：diagnose 的 0 表示范围内检查完整且无阻断，1 为存在阻断，2 为输入错误、模型不支持或证据不足。两者同时存在时优先 2，报告仍保留阻断。compare 和 trace 的语义、参数和 JSON 错误契约见 [CLI 文档](cli.md)。

已实现范围：Linux ELF64 小端 x86-64 glibc 依赖解析、直接和间接库选择、精确符号版本需求、启动作用域强符号检查、GNU property ISA 等级和 ABI-tag 最低内核要求。CPU hwcaps、旧 cache 格式、复杂作用域等未支持情形明确输出 unknown。元数据检查不能证明完整 ABI 或运行语义兼容。

## 呈现方式

默认先显示结论和阻断问题，再展示证据链。用户能从“libfoo.so 缺少 GLIBC_2.34”追溯至请求方、目标实际选中的 libc、版本需求与定义，而不必自行拼接多个工具输出。

已实现 `diagnose --interactive`，复用同一诊断模型，提供结论、问题与引入链、搜索证据、环境四个页面。CLI 支持保存事件和 A/B 对比；更细致的图形化过程回放仍为后续交互增强。原有概览、节区和反汇编作为辅助视图保留。

修复建议指向可验证的动作，如使用兼容目标的构建基线/sysroot、修复部署依赖或库搜索配置；不将“随意复制 libc”或“同名库建立软链接”作为通用修复。

## 实施阶段与验收

| 阶段 | 内容 | 验收要求 |
| --- | --- | --- |
| 当前基线 | 既有 TUI 与非交互静态报告 | 重定向无终端控制符；动态/静态 ELF 和 so 可检查；损坏输入明确失败 |
| 第一阶段（基础已实现） | glibc 启动兼容性：解释器、递归库解析、架构、符号和版本 | 可复现缺解释器、间接库缺失、错误库命中、版本缺失；报告完整证据链 |
| 第二阶段（基础已实现） | 保存诊断 JSON 快照和 A/B 对比 | 可指出同一产物在两环境中首次发生差异的解析步骤；离线分析不泄漏到宿主搜索路径 |
| 第三阶段（基础已实现） | 显式运行观测、日志导入和路径级推演对照 | 捕获插件加载、延迟绑定；清楚区分静态声明、推演和实测 |
| 后续 | 完整 CPU/内核行为、深层 ABI、其他架构和加载器（已有显式 GNU 元数据检查） | 对无法证明的情况报告未知，避免错误的“兼容”结论 |

关键测试样本应包含 RPATH 继承与 RUNPATH 作用域、重复/循环依赖、缺失符号版本、无普通符号表、无节区表、静态 ELF、错误格式及损坏文件。实际加载器作为规则校验依据，不能只测试自建解析器的内部一致性。

## 参考项目

- [libtree](https://github.com/haampie/libtree)：依赖树和库查找原因。
- [rldd](https://github.com/zatrazz/rldd)：加载器规则模拟和搜索路径。
- [ELF Dissector](https://github.com/KDE/elf-dissector)：符号依赖、重定位及加载分析。
- [glibc 动态链接器诊断](https://sourceware.org/glibc/manual/latest/html_node/Dynamic-Linker-Environment-Variables.html)：实际观测的证据来源之一。
